# 诊断与适配

## 已验证故障

Windows 客户端 `9.5.3.1001` 的播放器资源 `kplayer/kuplayer/4.24.1-xmedia/index.js` 是独立更新的。实测 VIP 账号中，优酷返回的独立手选流没有普通 4K 播放源，列出的帧享 4K 状态为 SVIP。优酷原有的普通 4K 偏好请求 `preferClarity=6` 回落到了 1080P。智能播放的自适应列表则下发了 `RESOLU=2160`、`QUALITY=6`、`STREAMTYPE="mp5hd4"` 的普通 4K。实际播放先以 `1920×1048` 解码，再自动切到 `3840×2088`。

补丁将同一会话已下发的普通 4K 作为 `智能 4K（固定）` 加入菜单。独立的副本保留原始变体行、签名地址、DRM 和同一播放器流程，再将可选档缩为一个。修改后手选及正常重启都测得 `3840×2160` 首帧，重启后的准备日志中也只有一个普通 4K 档。

## 换版时重新找入口

- 从优酷进程实际路径、卸载记录中的 `DisplayIcon` 和 `YOUKU.exe` 文件版本交叉核对客户端。这些信息用于定位和记录测试范围。以对应播放器和主进程的实际代码判断能否应用。
- 脚本从 `%APPDATA%\youku-app\layout_caches` 下的播放页读取官方播放器资源地址，再定位 `%APPDATA%\youku-app\local_caches` 下的对应脚本。有多个不同候选时，用当前播放窗口实际加载的脚本确认生效位置。同一个安装包里的旧 `play.html` 可能与活动的播放页不同。
- 只读核对当前影片的 `mediaData.multiQuality`、`mediaResource.streamList` 和自适应清单的画质元数据。手选条目来源和自适应清单属于两条路径。必要时用只监听本机的临时调试实例，退出后正常重开。保留账号正常使用的登录状态，不导出源地址或鉴权字段。
- 当前改动点是播放器的 `setMultiQuality` 和 `getStream`。前者决定可显示的画质，后者保持原播放器的载入方式。适配时确认新版本仍有对应职责，也确认从其他清晰度切过来和切回「智能」的行为。已知解析器只识别当前优酷的简单两行变体格式和已验证的 `mp5hd4` 档。扩展时应验证音轨引用、分离的媒体组、DRM 和无此画质影片的行为。
- 遇到只有 SVIP 的版本、账号无可用普通 4K、或来源未验证的 HDR 条目时停在实际已获授权的播放能力。保持官方会员校验及显式付费/试用行为。

## 验证与故障定位

- 原生播放器日志在 `%APPDATA%\youku\nplayer\nplayer_runtime_info-*-MainPlayer.log`。新播放开始后使用新近创建的文件，并结合全片时长区分不同影片。检查 `FirstFrame`、`video width:3840` 或 `UpdateVideoData size changed: frame=3840x…`。影视裁边会使高度小于 `2160`。
- 固定档的证据包括实际点击、应用记录为 `4k`、与点击时间对应的实际 4K 首帧，以及准备播放记录只包含 `RESOLU=2160` 的一个普通变体。分析日志时只显示必要的时间、分辨率、画质档号和类型。日志原文可能含签名和设备信息。
- `main.prod.js` 的优酷更新处理器有手动和后台入口，自动清理源于远程资源版本递增触发资源缓存删除。升级后应重新找调用方，保留手动入口。不要靠阻断整个域名、冻结整个目录或禁用系统更新来保护这个补丁。
- 自动清理保护范围仅为优酷主进程自动清空自有资源缓存的路径。远程播放页切换到另一个脚本版本、手动清除、系统工具清理、手动重装仍可能使补丁失效。重新排查当前版本并适配。
